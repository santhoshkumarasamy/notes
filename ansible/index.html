Ansible Notes

A quick reference covering password-less SSH setup, inventories, ad-hoc commands, playbooks, and roles.

🔐 Configuring Password-Less SSH

Password-less authentication in Ansible is achieved using SSH key pairs instead of passwords. Generate an SSH key and configure Ansible to use the private key. 

ssh-keygen -t ed25519 -a 100 -f ~/.ssh/my-server-key -C "prod-server"
Tip: Copy the generated public key (my-server-key.pub) to the ~/.ssh/authorized_keys file on the target server.

⚙️ Installing Ansible

python3 -m pip install ansible
If pip is not installed, install it before installing Ansible.

📦 Creating an Inventory File

Ansible inventories can be written in either INI or YAML format. YAML is generally easier to read and maintain.

Inventory Structure

all:
    vars:
    children:
        [group]:
            vars:
            hosts:
                [your own hostname]

Example Inventory

all:
  children:
    webservers:
      vars:
        ansible_ssh_private_key_file: /home/ec2-user/.ssh/my-server-key
        ansible_user: ec2-user
      hosts:
        host1:
          ansible_host: 172.31.20.235

Verify Inventory

ansible-inventory -i inventory.yaml --graph
ansible-inventory -i inventory.yaml --list

💻 Ad-hoc Commands

Ad-hoc commands allow you to execute one-time tasks without writing a playbook. 

ansible -i inventory.yaml -m ping all
ansible -i inventory.yaml -m shell -a "ls /" all

📖 Playbooks

A Playbook is a YAML file that defines a series of tasks to execute on managed hosts. Each play maps a group of hosts to a list of automation tasks.

Sample Playbook

---

- hosts: webservers
  become: yes

  tasks:

    - name: Install apache httpd
      ansible.builtin.yum:
        name: httpd
        state: present
        update_cache: yes

    - name: Copy sample file
      ansible.builtin.copy:
        src: ./index.html
        dest: /var/www/html
        owner: root
        group: root
        mode: '0644'

    - name: Start the service
      ansible.builtin.service:
        name: httpd
        state: started

Run a Playbook

ansible-playbook -i inventory.yaml httpd-play/apache-play.yaml

🧩 Roles

As playbooks grow, managing everything in a single file becomes difficult. Roles provide a standardized directory structure to organize reusable automation.

Create a Role

ansible-galaxy role init httpd-test

Generated Directory Structure

httpd-test
├── README.md
├── defaults
│   └── main.yml
├── files
├── handlers
│   └── main.yml
├── meta
│   └── main.yml
├── tasks
│   └── main.yml
├── templates
├── tests
│   ├── inventory
│   └── test.yml
└── vars
    └── main.yml

Role Directories

  • defaults – Default variables for the role.
  • files – Static files copied directly to managed hosts.
  • handlers – Triggered tasks such as restarting services.
  • meta – Role metadata and dependencies.
  • tasks – Main list of tasks executed by the role.
  • templates – Jinja2 templates for dynamic configuration files.
  • vars – Variables specific to the role.

Main Playbook

- hosts: webservers
  become: yes

  roles:
    - httpd-test

tasks/main.yml

---

- name: Install apache httpd
  ansible.builtin.yum:
    name: httpd
    state: present
    update_cache: yes

- name: Copy sample file
  ansible.builtin.copy:
    src: files/index.html
    dest: /var/www/html
    owner: root
    group: root
    mode: '0644'
  notify:
    - restart_httpd

handlers/main.yml

---

- name: start_httpd
  ansible.builtin.service:
    name: httpd
    state: started

- name: restart_httpd
  ansible.builtin.service:
    name: httpd
    state: restarted

📌 Using AWS Collections with Ansible Vault

Collections are similar to roles, but they are used for interacting with APIs instead of Linux or Windows commands. In this example, we'll use the AWS collection.

Install the AWS Collection

Install the AWS collection using Ansible Galaxy. 

ansible-galaxy collection install amazon.aws

You might already have this collection installed.

Install boto3

The AWS collection requires the Amazon SDK (boto3) as a dependency. 

python3 -m pip install boto3

Store AWS Credentials Securely

AWS requires authentication using an Access Key and Secret Key. While you can pass them as variables, this is insecure. Instead, use Ansible Vault to securely store them.

First, generate a random password for the vault. 

openssl rand -base64 2048 > vault.pass

Create the encrypted vault file using the password. 

ansible-vault create pass.yaml --vault-password-file vault.pass

The editor will open. Add your variables in YAML format, then save and close it. The generated file will be encrypted.

To decrypt the vault: 

ansible-vault decrypt pass.yaml --vault-password-file vault.pass

To encrypt it again: 

ansible-vault encrypt pass.yaml --vault-password-file vault.pass

Create the Playbook

Now that the prerequisites are ready, create a playbook to collect EC2 instance information. 

---
- hosts: localhost
  connection: local

  vars_files:
    - pass.yaml

  tasks:
    - name: Start the EC2 instance
      amazon.aws.ec2_instance_info:
        region: us-east-1
        access_key: "{{ aws_access_key }}"
        secret_key: "{{ aws_secret_key }}"
        instance_ids:
          - i-0efad667e6ea71f22

Run the Playbook

Running the playbook without the vault password results in the following error. 

ansible-playbook ec2-create.yaml

# [WARNING]: No inventory was parsed, only implicit localhost is available
# [WARNING]: provided hosts list is empty, only localhost is available.
# ERROR! Attempting to decrypt but no vault secrets found

Pass the vault password file when running the playbook. 

ansible-playbook ec2-create.yaml --vault-password-file vault.pass

The playbook will run successfully, but it won't display any output because it is only collecting information.

We can improve the playbook later by using a variable to print the collected details to the console.

🔁 Loops in Ansible

Loops allow you to execute the same task multiple times using different values. Instead of writing identical tasks repeatedly, you can define a list of values and iterate through them using the loop keyword.

Tip: Store repeated values in a variable file and iterate over them using loop. This keeps playbooks clean and reusable.
Note: Each iteration is accessible through the special variable item.
Warning: When creating multiple cloud resources, ensure that each iteration has a unique attribute (such as a name or tag). Otherwise, Ansible's idempotent behavior may treat them as the same resource.

Main Playbook

Instead of specifying AWS credentials inside every task, they can be configured once using environment variables. The values are securely loaded from an Ansible Vault file. 

---
- hosts: localhost
  connection: local

  vars_files:
    - pass.yaml

  environment:
    AWS_ACCESS_KEY_ID: "{{ aws_access_key }}"
    AWS_SECRET_ACCESS_KEY: "{{ aws_secret_key }}"
    AWS_DEFAULT_REGION: "us-east-1"

  roles:
    - project

Task Using Loop

The task below creates (or manages) EC2 instances by looping through each item defined in the variable instances. 

---
- name: Start an EC2 instance
  amazon.aws.ec2_instance:
    name: "{{ item.env_name }}"
    vpc_subnet_id: subnet-0bd2c4ee2ee4d0762
    instance_type: t2.micro
    security_group: default

    network_interfaces:
      - assign_public_ip: true

    image_id: "{{ item.ami_id }}"

    tags:
      Environment: "{{ item.env_name }}"

    state: terminated

  loop: "{{ instances }}"

Variable File

Each list item contains the values required during one iteration of the loop. 

---
instances:
  - ami_id: ami-0b826bb6d96d2afe4
    env_name: dev

  - ami_id: ami-0b826bb6d96d2afe4
    env_name: test

  - ami_id: ami-0b826bb6d96d2afe4
    env_name: prod

Why include env_name?

You may wonder why the environment name is included when all instances use the same AMI ID.

Consider the following variable: 

ami_id:
  - ami-0b826bb6d96d2afe4
  - ami-0b826bb6d96d2afe4
  - ami-0b826bb6d96d2afe4

If only the AMI ID is supplied, every loop iteration requests an identical resource. Since Ansible is idempotent, it compares the desired state with the existing state and determines that the resource already exists. As a result, it does not create multiple identical instances.

Note: Adding a unique value such as the instance name, tags, or environment ensures that every iteration represents a different resource.
Variable Purpose
ami_id AMI used to launch the EC2 instance.
env_name Provides a unique name and tag for each instance.
item Represents the current object during each loop iteration.

⚡ Conditions in Ansible

Conditions allow a task to execute only when a specific expression evaluates to true. The keyword used for conditional execution is when.

Tip: Conditions are commonly used with facts gathered from managed hosts.
Note: Ansible facts are automatically collected at the beginning of a play unless fact gathering is disabled.
Warning: Ensure the condition matches the intended operating system or host. An incorrect condition may prevent the task from executing.

Example Using when

---
- hosts: all
  become: true

  tasks:
    - name: Print gathered facts
      ansible.builtin.debug:
        var: ansible_facts

    - name: Stop the server if it is RedHat
      ansible.builtin.command: /sbin/shutdown -t now
      when:
        ansible_facts.os_family == "RedHat"

In this example, the shutdown command runs only if the managed host belongs to the RedHat operating system family.

  • when evaluates a Boolean expression.
  • The task executes only if the expression is true.
  • Facts such as ansible_facts.os_family are commonly used in conditions.
Keyword Description
loop Repeats a task for each item in a list.
item Current value during a loop iteration.
when Executes a task only when the specified condition is true.
ansible_facts System information collected from managed hosts.

📌 Error Handling in Ansible

By default, if a task fails on a host, Ansible stops executing all the remaining tasks for that host. This is useful because it prevents subsequent tasks from running when a previous step has already failed. However, there are situations where you want Ansible to continue even if a task fails. This is where ignore_errors becomes useful.

Tip: Use ignore_errors: true when a failed task should not stop the remaining tasks from executing.
Note: Even when a task is ignored, Ansible still records the failure. You can access the task result using the register keyword.
Warning: Avoid using ignore_errors everywhere. It can hide real problems if used without proper validation.

Continue Execution Even When a Task Fails

In the following playbook, Ansible checks whether tmux is installed by running tmux -V. If the command fails, Ansible ignores the error and continues to the next task. 

---
- hosts: all
  become: true

  tasks:
    - name: make sure tmux is present
      ansible.builtin.command: "tmux -V"
      register: output
      ignore_errors: true

    - name: print the log
      debug:
        var: output

Since the command output is stored in the variable output, the next task prints all the details including whether the task failed.

Keyword Purpose
register Stores the output of a task in a variable.
ignore_errors Continues executing the remaining tasks even if the current task fails.
debug Displays the contents of a variable.

Install a Package Only if the Previous Task Failed

Since the task result is stored using register, you can use it in a when condition. 

---
- hosts: all
  become: true

  tasks:
    - name: make sure tmux is present
      ansible.builtin.command: "tmux -V"
      register: output
      ignore_errors: true

    - name: print the log
      debug:
        var: output

    - name: install tmux if not there
      ansible.builtin.yum:
        name: tmux
        state: latest
      when:
        - output.failed

If tmux -V fails, output.failed becomes true, causing the installation task to run. If the command succeeds, the installation task is skipped.

Tip: Using register together with when is a common pattern for building self-healing playbooks.

📌 Conditional Task Failure with failed_when

Sometimes a command succeeds, but you still want Ansible to treat it as a failure. This can be done using the failed_when condition. 

---
- hosts: all
  become: true

  tasks:
    - name: is folder available
      ansible.builtin.command: "ls /tmp"
      register: output
      failed_when: true
      ignore_errors: true

    - name: print the log
      debug:
        var: output

The command ls /tmp executes successfully, but failed_when: true forces Ansible to mark the task as failed. Since ignore_errors is also enabled, execution continues to the next task.

Note: The command output is still available in output.stdout, even though the task is marked as failed.

Ignore Specific Errors Using failed_when

You can also use failed_when to prevent Ansible from failing for expected errors. 

---
- hosts: all
  become: true

  tasks:
    - name: is folder available
      ansible.builtin.command: "ls /tmp/itisnotthere"
      register: output
      failed_when: "'No such' not in output.stderr"

    - name: print the log
      debug:
        var: output

The command attempts to list a directory that does not exist. Normally this would fail, but the failed_when condition tells Ansible that the task should only fail if the text No such is not present in the error message.

Since the error message contains No such file or directory, the condition evaluates to false, so Ansible considers the task successful and continues with the remaining tasks.

Feature Use Case
ignore_errors Continue execution even when a task fails.
register Save task output for later use.
when Run tasks conditionally based on previous results.
failed_when Customize when a task should be considered failed.
